# law-map

Machine-readable **obligation graph**: law organized as technical obligations
mapped to jurisdiction groundings.

Instead of a flat "regulations" table, law-map stores *deontic rules you can
implement* (prohibitions, obligations, permissions) with the legal sources
that ground them — statutes, regulations, precedent, and guidance alike.
The unifying idea is **functional equivalence**: when a Japanese statute, an
EU regulation and a US FTC enforcement action all require the same technical
behavior, they are one obligation node with multiple groundings.

**Japan-first, global-ready.** The goal is every jurisdiction; the corpus
today is small and centred on Japan, the EU and the US, the markets a
Japanese software team ships to first. The table below is the honest
current scope — groundings counted by how binding they are, not just how
many there are.

## Roadmap

New jurisdictions and domains are picked by four criteria: (1) it is a market
users ship software to, (2) the law reduces to technical obligations, (3)
primary sources can be fetched mechanically (open-law has an adapter), and
(4) a reviewer who reads that jurisdiction's law is available.

Next jurisdictions:

- United Kingdom (`GB`), South Korea (`KR`), Canada (`CA`) and Germany
  (`DE`): open-law already has adapters for them, and each has zero to two
  groundings today
- US state privacy laws beyond California (`US` with a `subdivision`)

Domains with no obligations yet:

- accessibility beyond the European Accessibility Act baseline (now its own category)
- children's data
- consumer protection and dark patterns
- cryptography export control
- platform regulation

Any of these, or a — cell in the tables above, is a good first
contribution; reviewers who read one of these jurisdictions are especially
welcome (see [Contributing](#contributing)).

## Layout

```
schemas/obligation.schema.yml   field reference (types, constraints, enums)
obligations/<domain>/<slug>.yml one obligation per file (reviewed by humans)
checks/<domain>/<slug>.yml      machine-check specs, optional per obligation
src/law_map/                    loader, validator, checker, exporter, CLI
tests/                          pytest suite (offline)
docs/why-law-map.md             design note: functional equivalence
.github/workflows/              ci.yml, drift-watch.yml (weekly review scan + law-watch)
```

## Quickstart

```bash
uv sync
uv run law-map validate            # load corpus, report every error/warning
uv run law-map validate --kanon kanon/   # also cross-check related_sections against a kanon checkout
uv run law-map list                # all obligation ids
uv run law-map show privacy/no-cleartext-pii-logging
uv run law-map check               # groundings due for review (default 30 days)
uv run law-map check --sources --days 30   # also HEAD-check source URLs
uv run law-map export --out out/   # kanon-style .md.jinja section skeletons
uv run law-map stats --markdown    # scope tables (the README "Scope today" block)
uv run law-map watch               # law-watch: were cited instruments amended? (network)
uv run law-map record-hashes       # dry-run: show open_law text hashes (`--write` records them)
uv run law-map migrate --in <v1-obligations> --out <dir>  # schema v1 -> v2 conversion
uv run law-map --pack core list    # load only one pack (repeatable; default: all)
uv run pytest -q
uv run ruff check .
uv run mypy src/law_map
```

Or with [just](https://github.com/casey/just): `just check` runs validate +
the README stats sync check + pytest + ruff + mypy.

## Packs

Every obligation belongs to one pack, derived from its strongest grounding's
`source_type` (no extra field to maintain):

| pack        | binding level                    | source types                          |
| ----------- | -------------------------------- | ------------------------------------- |
| `core`      | binding law                      | `statute`, `regulation`, `precedent`  |
| `guidance`  | official guidance and standards  | `guidance`, `standard`, `model_code`  |
| `community` | not a legal source               | `private_rule`, `incident_report`     |

`--pack` (repeatable, before the subcommand) selects which packs are loaded;
the default is all three. Every file is still validated, and
`requires`/`conflicts` resolve across packs, so a `core` obligation may
depend on a `community` lesson and both keep working together.

## Validation contract

`law-map validate` exits non-zero if the corpus violates any rule in
`schemas/obligation.schema.yml` (implemented in `src/law_map/model.py`):
schema `version: 2` (v1 files name the fix: `law-map migrate --in
<v1-obligations> --out <dir>`), required fields, enums, id pattern
(`obligation.<domain>.<slug>`) and uniqueness, grounding shape
(jurisdiction, source_type, required `source_kind`, status, authority,
citation, ISO `review_by`, non-empty http(s) `sources`, optional `open_law`
`{source, id}` ref into open-law for amendment detection, optional ISO
`reviewed_on`, optional `verified_text_sha256`, `scope`/`exceptions`/`strength`,
`negative_history`), at least one `primary` grounding per obligation,
subdivisions as ISO 3166-2 codes, `L2` specs only with an executable
`blocking` rule and existing `fixtures` (one spec per obligation), peer-review
shape (`reviewed_by` handle+domain with `reviewed_on`; missing review displays
as `draft`), and cross-references
(`requires`/`conflicts` ids, `enforcement.check_refs` files). Files whose
basename starts with `_` are excluded from the corpus (see
`obligations/_example.yml`). `related_sections` ids (`<tier>-<slug>`) are
resolved only with `--kanon <checkout>`: then each must resolve to
`sections/<tier>/<slug>.md.jinja` per the `<tier>-<slug>` naming rule, and an id
not present becomes an error, while kanon sections that no obligation's
`related_sections` references are reported as warnings (reverse coverage),
never errors. Without `--kanon` the ids are unchecked.

## Review freshness

Every grounding carries a `review_by` date — the freshness contract. A grounding
may also carry an optional `open_law` ref (`{source: <open-law source_id>, id:
<source-native law id>}`, e.g. `{source: jp, id: 415AC0000000057}` for APPI or
`{source: eu, id: 32016R0679}` for GDPR) that `law-map check --sources` resolves
through `open_adapter(source).fetch(id)`: an upstream `modified` newer than the
grounding's `effective` date is reported as `[open-law amended]`, and fetched
text hashing differently from the grounding's `verified_text_sha256` as
`[open-law changed]` (record hashes with `law-map record-hashes --write`;
every grounding of the same law is compared, fetching deduplicates). Each
probe carries a sha256 of the fetched text. Refs skip silently when the
`open-law` package is not installed
The weekly `drift-watch` workflow runs `law-map check --sources --days 30` and
opens one GitHub issue (`law-drift` label) listing groundings due or expired,
source URLs that now 404 or redirect, plus amended or unreachable open-law refs;
when a run is clean it closes any open `law-drift` issue with a "drift resolved"
comment. `law-map check` exits 1 when any grounding is expired, so the workflow
can gate on it.

Dates alone miss a law that changes before its `review_by` (the EU AI Omnibus
moved AI Act deadlines months ahead of every review date). The same workflow
therefore runs a **law-watch** job: `law-map watch` asks each cited
instrument's publisher whether it was amended after the grounding was last
verified — EUR-Lex (amending acts recorded against the CELEX, e.g.
`32024R1689`), e-Gov (API v2 revision history), and legislation.gov.uk (the
act's changes feed). Instruments come from `open_law` refs and source URLs.
The baseline is the grounding's `reviewed_on` date, else its `effective` date
(`scheduled`/`proposed` groundings need `reviewed_on`). Each newer amendment
prints `[law-watch changed] <id> groundings[<n>] <kind>:<instrument>: amended
<date> by <act> (...)`, the command exits 1, and the job opens or updates one
`law-watch` issue (closed again on a clean run). After re-verifying a
grounding, set `reviewed_on` to the date you checked it.

## Pipeline

```bash
just pipeline   # upstream→downstream: validate the corpus, then review-freshness check
```

`just pipeline` runs `uv run law-map validate && uv run law-map check --days 30`.
`law-map check --days 30` prints one `[EXPIRED] <id> (<jurisdiction>): <citation>`
or `[due by <review_by>] ...` line per grounding due within the horizon, and exits 1
when any grounding is expired. With `--sources` it additionally HEAD-checks grounding
source URLs (`[source <not-found|redirect|unreachable>] <url>` plus a
`source probes: <N> total, <M> flagged` line) and resolves every grounding `open_law`
ref (`[open-law <amended|unavailable|unreachable>] <id> <source>:<law_id>`,
`[skipped] <id>: ...` when the `open-law` package is not installed, plus an
`open-law probes: <N> total, <M> flagged, skipped: <K>` line). The run ends with
`review check: <D> due within 30 day(s), 0 expired` on success.
